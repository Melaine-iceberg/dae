# 文件标签的存储：文件流 + 分片索引

> 日期：2026-11-05 · 状态：已实施（P0）
> 相关：`docs/files-parity.md` §5.1/§10.1、`crates/dae-core/src/fs/tags.rs`

## 问题

标签必须同时满足三件互相拉扯的事：

1. 跟着文件走：把文件移到另一个目录、拷到另一台机器，标签还在。
2. 可查询：`tag:` 搜索、侧栏计数、按标签排序/分组要能回答，而不能为了一个
   计数遍历整块磁盘。
3. 跨平台、可降级：NTFS、APFS、ext4 能存扩展属性；exFAT、SMB、SFTP、压缩包
   不能。不能存的时候功能必须仍然可用，且用户要知道标签没有随文件走。

## 决定

**两层都写，各司其职。**

| 层 | 位置 | 角色 |
| --- | --- | --- |
| 文件流 | Windows NTFS ADS `dae.tags`；Linux `user.dae.tags`；macOS `com.dae.tags` | 让标签随文件移动；值是 UTF-8 JSON 数组（标签 id） |
| 索引 | `<config>/tags-index/<volume>-<fnv64>.json`，按卷/远程主机分片 | `tag:` 搜索、计数、排序/分组的唯一查询来源；也是远程/压缩包的唯一存储 |

写入时两层都更新；读取时索引优先，索引没有该路径时回退文件流（覆盖「文件从
别处拷进来」的情况）。清空标签会删除文件流并从索引移除条目，而不是写一个空数组。

卷是否支持文件流**按卷探测一次并缓存**（在目录里建临时文件、写读删），失败即
只写索引，界面用一句 `TagStore.note` 说明边界。远程路径、压缩包、云盘直接跳过
探测，只写索引。

索引键是折叠路径（Windows/macOS 小写化）；Unix 额外记录 `dev:ino` 供将来在
watcher 里做改名关联，但当前版本不承诺外部改名后保留标签。

## 为什么不选别的

- **只写文件流（Files 的做法）**：exFAT/网络/压缩包会静默丢标签；`tag:` 搜索与
  计数要遍历磁盘。这是 `files-parity.md` §8 明确列出的「不复制」的限制。
- **只写索引**：标签不会随文件走，换机器就没了；与「文件标签」的直觉相悖。
- **引入 SQLite（`rusqlite`）**：当前量级（单用户、几千到几万条关联）用分片
  JSON + 原子写足够；SQLite 增加一个 C 依赖和迁移/损坏处理，收益要等 10 万条
  级别的实测再评估。真正需要时，`TagStore` 的查询接口（`tags_for`、
  `paths_with_tags`、`counts`）可以换成数据库实现而不动 UI。
- **macOS 同时写 Finder 标签（`kMDItemUserTags`）**：binary plist 是 macOS 专有
  格式，写失败不能影响主存储；按计划默认关闭，不在本轮实现（P2-3）。

## 后果

- 删除标签定义只从定义文件和索引里剥掉 id，不回写每个文件的流。没有定义指向
  的 id 在读取时被忽略，代价是文件流里可能留下无害的死 id。
- 外部改名（Explorer、`mv`、同步工具）会让索引条目与文件失联；索引不会自动
  跟着改名。恢复方式是重新打标，或将来用已记录的 `dev:ino` 在 watcher 里修补。
- 复制一个已打标的文件到新路径，新路径没有索引条目，读取会回退文件流并显示
  标签；下一次写入会把新路径写进索引。
- 列表枚举不读标签；标签只在列表完成后按可见行批量读取（`requestTags`），
  按标签排序/分组时才全量读取，且在工作线程。`docs/decisions/listing-shell-costs.md`
  的枚举预算因此不变。
- 分片 JSON 的写入全部经过 `INDEX_LOCK` 与原子替换；一个损坏的分片只丢失该
  卷的标签索引，不会影响其他卷或标签定义。

## 何时重新考虑

- 索引条目达到 10 万级、分片解析成为搜索或排序的可见开销；
- 需要跨设备同步标签、或需要多进程同时写（当前假设单进程）；
- Windows Search 索引在 MSIX 形态下可验证并愿意把标签查询交给系统索引
  （`files-parity.md` §5.5 阶段 2）。

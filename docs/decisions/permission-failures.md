# 权限失败的两种答案：提权重试与占用者查询

> 日期：2026-11-09 · 状态：**已实施**（macOS 分支未在真机验证）
> 对象：`crates/dae-core/src/fs/elevated.rs`、`fs/occupancy.rs`、`fs/service.rs`、
> `apps/dae/src/main.rs`、`crates/dae-qt/src/workspace.rs`、`qml/StatusCenter.qml`

一次复制或删除失败时，「拒绝访问」这四个字对用户没有信息量。它能是两件完全
不同的事：**这个进程的权限不够**，或者**另一个程序正占着这个文件**。两份答案
对应两条完全不同的出路，所以分开处理：

| 症状 | 出路 | 实现 |
|---|---|---|
| 目标是受保护目录（`Program Files`、`System32`、别的用户目录） | 把这**一次操作**交给提权进程重放 | `fs/elevated.rs` + `--elevated-job` |
| 文件被别的程序打开着 | 在错误信息里点名是哪个进程 | `fs/occupancy.rs` |

---

## 1. 提权的是操作，不是应用

**结论：整个窗口、列表、终端、索引都留在用户自己的令牌下；只有一次复制/移动
会以管理员身份重放。**

反过来做（以管理员身份重启整个应用）有几个具体后果，都不是风格问题：

1. 提权后的进程会拿到一批**用户本不该有的句柄**：文件、目录、注册表，全部
   带着管理员令牌。浏览器的下载目录、别的用户的 profile 都会变得「可写」，
   而 UI 上没有任何东西提示这一点。
2. 单实例锁（`activation::claim`）在提权进程里会**抢走**普通进程的
   `dae://` 与命令行转发，于是「用管理员开一次」变成「以后都是管理员」。
3. 一次失败的重试需要的权限，和接下来每一次浏览需要的权限，量级差得很远。

### 协议

1. 窗口把这次操作写成一份 **job**：`{kind, sources[], destination}`，
   落在 `{config}/elevated/<pid>-<ms>.json`。
2. 用自己的可执行文件以 `--elevated-job <path>` 拉起自己：
   - Windows：`ShellExecuteExW` + `lpVerb = "runas"`，等子进程退出；
   - Linux：`pkexec <exe> --elevated-job <path>`（没有 `pkexec` 就直说）；
   - macOS：`osascript -e 'do shell script … with administrator privileges'`。
3. 子进程在 **Qt 初始化之前**回答（`main` 的第一件事就是
   `dae_qt::elevated::run_from_args()`）：用同一套传输引擎执行，写一份
   `*.result.json`，退出。它不建窗口、不取实例锁、不加载 QML。
4. 父进程读结果文件，成功即成功，失败即把子进程的原文当错误报出来。

**为什么用文件通信而不是管道**：两边是不同权限级别的进程，中间隔着一次 UAC
或 polkit 会话；管道在任一端崩溃时的语义是「读阻塞到超时」，结果文件的语义是
「没有文件 = 子进程没答上来」。后者的失败信息更有用。

### 信任边界

`--elevated-job` 是提权进程接受外部输入的唯一入口，因此只接受**本目录**里的
job（`{config}/elevated/`，按用户隔离、非全局可写）。否则任何能以当前用户身份
写一个 JSON 的人都能让 dae 帮他以管理员身份搬文件 —— 用户还得为此点一次 UAC。

这条检查带来一个已知限制：**标准用户 + 另一个管理员账户**（UAC 的
over-the-shoulder 形态）提权时，子进程以那个管理员身份运行，`{config}` 解析到
的目录不同，job 会被拒绝、操作失败并如实报错。管理员账户自身的 UAC 提权是同一
用户、同一目录，不受影响。要覆盖前者，需要另立一条信任规则（例如用一次性令牌
代替路径校验），在那之前**拒绝**比放松边界更合适 —— 失败是可见的，越权是静默的。

job 执行完即删除，结果文件同样。没有历史、没有队列、不可重放。

### 代价，明确写下来

- **没有进度**。子进程报不进父进程的事件循环，父进程只能等。所以状态行是
  不定长的（`progressTotal = 0` 即不定进度），文案是「以管理员身份复制中…」。
- **只有复制和移动有这条路**。解压需要密码、删除失败通常是占用而非权限，
  两者都不该变成一次 UAC。删除失败交给 §2 的占用者查询。
- **只有失败之后才提供**。不做「预判会失败就提前提权」——那需要先探一次
  `access`，而探测的答案在真正写入时可能已经变了，白弹一次 UAC 更糟。

重新考虑的条件：如果出现「提权复制大目录时，用户因为看不到进度而以为卡死」的
反馈，再评估让子进程往一个 journal 文件里追加进度、父进程轮询 —— 但那等于
再造一条进度通道，先要有真实反馈。

## 2. 占用者查询：三个平台，三种机制，都不保证

| 平台 | 机制 | 成本 | 备注 |
|---|---|---|---|
| Windows | Restart Manager（`rstrtmgr.dll`） | 一次会话，约 1 ms | 与「文件正在使用」对话框同一份数据 |
| Linux | 遍历 `/proc/<pid>/fd` 的符号链接 | 5–40 ms | 只读，不需要额外权限；跳过本进程 |
| macOS | `lsof -F pc -- <paths>` | 约 50 ms | 需要子进程 |

**为什么不做一个「占用进程」面板**：这个问题只在失败的那一刻有意义。用户不会
平时去查「谁开着这个文件」，而失败时他需要的是**一句话**，不是一个列表。所以
唯一的接入点是错误信息：

```
拒绝访问。 (os error 5)（占用：Code.exe (4120)）
```

`annotate_lock_error` 只在 `PermissionDenied` / `Io` / `Internal` 上追加，
最多点名三个进程（更多名字没人读），并且**查不到就原样返回** —— 诊断信息绝不
能把真实错误替换掉。

Linux 跳过本进程：dae 自己的预览可能正开着那个文件，把「自己」报成占用者会让
用户去关一个他正在看的预览 —— 那是噪音，不是答案。

三条实现都是 best-effort：探测失败返回「没人占用」。这是有意的 —— 一个查询
失败不应该让一次删除失败变成两次。

重新考虑的条件：如果 Windows 上出现 Restart Manager 查不到、但删除仍然失败的
高频反馈（例如服务进程持有目录句柄），再评估对**父目录**也做一次查询，并附上
「卷上有打开的文件」这类无法归因的兜底文案。

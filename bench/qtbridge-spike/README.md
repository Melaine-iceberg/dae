# qtbridge_spike — what the Qt Bridge migration has to keep

> The execution handoff — branch state, per-module recipe, remaining work and
> known gaps — is [`docs/decisions/qtbridge-migration.md`](../../docs/decisions/qtbridge-migration.md).

Feasibility gate for moving `crates/dae-qt` from CXX-Qt 0.10 to
[Qt Bridge for Rust](https://doc.qt.io/qtbridge-rust/) 0.4.1 (beta, MSRV 1.88,
Qt ≥ 6.10; this machine runs Qt 6.12.0 / MSVC 2022).

Qt Bridge deliberately hides the Qt object model behind dynamic
`QMetaObject`s built at runtime instead of per-type C++ generated by a build
script. That deletes `cxx-qt-build`, `moc`-per-type and the `qobject` C++ glue,
but three seams the shell depends on are not part of its API. This binary
exercises each one before the 28k-line bridge is rewritten.

## Result

Passed on Windows 11, Qt 6.12.0, `qtbridge` 0.4.1:

```
[spike] mark 1/6: model-count:3
[spike] mark 2/6: model-count:3
[spike] mark 3/6: image:4x4
[spike] mark 4/6: qml-count:3
[spike] mark 5/6: cpp-item:42:cpp-item
[spike] mark 6/6: model-row:alpha.txt 12
```

| Seam in `crates/dae-qt` | Qt Bridge equivalent | Verified |
|---|---|---|
| `#[qproperty]`, `#[qsignal]`, `#[qinvokable]`, `QString` args | `qproperty!`, `#[qsignal]`, `#[qslot]` (`String`, owned) | yes — `Backend.count` reached QML as 3 after three slot calls |
| `QAbstractListModel` + 26 roles + manual `beginInsertRows`/`dataChanged` | `QAbstractItemModel` base (`index`/`parent`/`row_count`/`data`/`role_names`, `QModelIndex` internal pointer, `QAbstractItemModelBase` notifiers) | yes — 3 rows, custom roles `fileName`/`sizeText`, delegate read `alpha.txt 12` |
| `QQuickImageProvider` registration on the engine | `QApp::qml_engine()` → our C++ `addImageProvider` | yes — `image://spike/test` resolved 4×4 |
| C++ `QQuickItem` registered as a QML type (`TerminalItem`) | same C++, separate module (`qmlRegisterType("dae.terminal")`) | yes — `SpikeItem.answer == 42` |
| `cxx-qt-build` (Qt discovery, moc, includes, links) | own `build.rs` with `qmake -query` + `cc` + `moc` | yes — 60 lines, see `build.rs` |
| Module and element names: 30 QML files say `import dae 1.0` | `#[qobject(NoQmlElement)]` + manual `QmlElement` impl (`URI = "dae"`, element name, `IS_SINGLETON`) | yes — QML read `Backend.count` through `import dae 1.0` |

The manual `QmlElement` impls matter more than they look: they keep the QML
surface identical while the bridge is ported, so **no `.qml` file changes** and
`qmlcachegen` keeps the same module name. `Singleton` cannot be combined with
`NoQmlElement` in the macro (it rejects the pair), so a singleton is declared
as a plain `#[qobject(NoQmlElement)]` and `IS_SINGLETON = true` is set on the
manual impl.

## Not covered here

* **QML AOT.** `apps/dae/build.rs` compiles the 53 documents with
  `qmlcachegen` and needs `qmldir` + `plugin.qmltypes` for `import dae`. Qt
  Bridge registers types at runtime and does not emit `qmltypes`
  ("Extend IDE support … types generated in Rust" is on its future list), so
  cold-start AOT (1120 → 860 ms, `docs/qml-aot.md`) has no input until a
  type-info emitter exists or upstream ships one. Because the module name stays
  `dae`, the build script can keep its `qmldir` and add each ported type as an
  `isTypeOpaque` entry, which is what `qmltc` already needs — a temporary
  fallback, not a full type description.
* **`QApp` owns the engine.** `qml_engine()` is `QQmlEngine*`; the shell's
  shell-first placeholder, deferred `engine.load` and `objectCreated` hook use
  `QQmlApplicationEngine`, so the C++ side needs a checked downcast (or an
  upstream accessor).
* **Threading.** `cxx_qt::Threading::qt_thread()` (55 uses, 15 impls) maps to
  `QThreadHandle`, which takes the `Rc<RefCell<T>>` at construction instead of
  being derived from the QObject.
* **`QByteArray` / `QVariant` properties.** Qt Bridge crosses `Vec<u8>` as
  `QList<u8>`, not `QByteArray`; the terminal frame and `writeByteData` need
  a converter on either side.

## Where the port stands

Ported so far, all verified by `cargo test -p dae-qt --lib` (217 pass), the
`DAE_QML_AOT/TYPEC/LINT` gate set and a real launch of `target/debug/dae.exe`
with no QML warnings:

| Module | Shape |
|---|---|
| `startup.rs` | singleton, one slot, no state |
| `session.rs` | singleton, 2 properties, 5 slots |
| `tags.rs` | singleton, 2 properties, 2 signals, 10 slots, `Vec<String>` |
| `config.rs` | element, 6 constant properties, C++ call kept in its cxx bridge |
| `appearance.rs` | singleton, 6 properties, 6 slots, `translator.h` extern kept |
| `network_discovery.rs` | singleton, 3 properties, 1 slot, `QThreadHandle` result |
| `preferences.rs` | singleton, 36 properties, 11 slots, `notifying_setters!` |

No `.qml` file changed for a port. Per module the pattern is:

1. `#[cxx_qt::bridge]`'s `RustQt` block becomes
   `#[qobject(NoQmlElement, ConvertToCamelCase)] impl` + a manual `QmlElement`
   impl (`URI = "dae"`, element name, `IS_SINGLETON`).
2. `QString` → `String`, `QStringList` → `Vec<String>`, `Pin<&mut Self>` →
   `&mut self`; generated setters (`self.as_mut().set_x(…)`) become field
   writes plus an explicit notify signal.
3. The file leaves `crates/dae-qt/build.rs`'s `.files([…])` list, and
   `dae_qt::init()` calls `Type::register()` before the engine exists.
4. A file that also calls C++ (e.g. `config.rs`'s `dae_qt_system_dark`) keeps
   its `#[cxx_qt::bridge]` `extern "C++"` block; only the `RustQt` half moves.

5. The ported type is described back into the QML metadata by
   `apps/dae/build.rs` (read from the `QmlElement`/`qproperty!`/`#[qslot]`
   declarations), so `qmltc` and `qmllint` keep resolving `import dae`.

Remaining, roughly in dependency order: the command/overlay models
(`shell_command_model`, `open_with_model`), the listing models
(`sidebar_model`, `sidebar_tree_model`, `spaces_model`, `trash_model`,
`overview_model`, `search_model`, `model`), then `workspace` (45 properties),
`window`/`terminal` (C++ calls and `QByteArray`), `preview`/`properties`, and
finally `apps/dae/main.rs` (`QApp`, engine downcast) — at which point
`cxx-qt-build`, the moc glue and the `#[cxx_qt::bridge]` remnants can go.

## Running

`qmake` has to be in `PATH` and `QMAKE` has to point at it in Windows form
(the build script passes it to `Command`):

```powershell
$env:PATH = "K:\Qt\6.12.0\msvc2022_64\bin;$env:PATH"
$env:QMAKE = "K:\Qt\6.12.0\msvc2022_64\bin\qmake.exe"
cargo run
```

The QML source is inline in `src/main.rs`; the window closes itself after two
seconds and the process exits 0 once all six marks printed.
